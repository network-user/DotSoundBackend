# Phase 4 из 8 — Публичный API релизов

## Общий контекст задачи (вся цепочка 1–8)

Каталог уже может заполняться синком (этап 3). Этот этап открывает **чтение** каталога для **mini app**: список релизов на карточке артиста и деталь релиза с треками. Не изменяет логику синка и не трогает админку.

Подробная матрица: [README.md](README.md).

## Роль этого этапа

**Этап 4 из 8.** **HTTP-граница для клиента:** публичные (или авторизованные по правилам проекта) эндпоинты, Pydantic-схемы, сервисы/репозитории без SQL в роутерах.

## Границы (анти-конфликты)

| Делает этот этап | Не делает |
|------------------|-----------|
| Расширение ответа артиста или отдельные GET для списка релизов и детали релиза | Изменение `SoundCloudService` или синк-сервиса (этапы 2–3) кроме мелких багфиксов по контракту |
| Схемы ответов для обложек/ track list для плеера | Верстку React mini app (этап 5) |
| pytest на API/сервис | Полный админский CRUD (этап 6) |

**Prerequisites:** этап 3 желателен (чтобы были данные); минимум — этап 1 и ручные строки в БД для контракт-тестов.

**Выход для этапа 5:** стабильные типы и URL, которые фронт может закодировать.

---

## Цель

Эндпоинты для mini app: краткий список релизов на карточке артиста; деталь релиза со списком треков и данными для плеера (без утечки лишних внутренних полей SC).

## Что делать

- Расширить ответ деталки артиста или отдельный endpoint списка релизов.
- `GET` деталки релиза с упорядоченными треками (`track_id`, позиция, метаданные для UI).
- Pydantic-схемы в `app/schemas/`, логика в services/repos; роуты без прямого SQL.

## Критерии готовности

- OpenAPI корректен; pytest на сервис/API по образцу проекта.
